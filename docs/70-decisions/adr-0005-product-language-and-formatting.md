# ADR-0005: Use English as the Only Product Language

## Status

Accepted

## Context

The current product is a server-rendered English workspace with HTMX fragments. The
visible templates, accessibility labels, page metadata, and user-facing messages from
Python are already written in English. The document and mail flows also display names,
case data, and imported message metadata that may be written in any language by users or
external correspondents.

The application has no locale selector, browser-locale resolution, translation catalog,
or locale-dependent number formatting. Date-time rendering is already centralized in
`goldenage.web.app` and uses the configured local time zone. Introducing translation
infrastructure without a supported user group or product requirement would add catalog,
fallback, and maintenance responsibilities without improving the current product.

## Decision

- English (`en`) is the only supported product language for the current release.
- There is no language selector and no browser or account locale resolution. Full pages
  and HTMX responses use the same fixed product language, and `base.html` keeps
  `<html lang="en">`.
- Product text includes headings, labels, buttons, accessibility text, empty states,
  status messages, validation errors, and server-side errors intended for users. These
  remain authored in English in templates or Python until a future product decision
  requires a catalog.
- User-owned and imported content is not product text and must not be translated or
  normalized as part of this decision. This includes display names, companies, case
  titles, activity descriptions, mail subjects and bodies, sender/recipient names, and
  other message metadata.
- Displayed date-times use `GOLDENAGE_LOCAL_TIMEZONE` (default: `Europe/Berlin`) and
  the fixed 24-hour format `DD.MM.YYYY HH:MM`. Missing date-times display as `n/a`.
  `datetime-local` form controls use the HTML wire format `YYYY-MM-DDTHH:MM`; submitted
  values are interpreted in the configured local time zone and persisted as UTC.
- Counts and limits are currently rendered as ungrouped decimal digits. No localized
  decimal, grouping, currency, or percentage formatting is supported because the
  product does not currently expose such values.
- If a language is not English, it is unsupported and there is no fallback catalog or
  language negotiation. A request for another supported language reopens this ADR and
  must define selection, fallback, placeholders, plural forms, formatting, ownership,
  and coverage before implementation.

## Consequences

- English-only is a complete product configuration and needs no i18n framework or
  extraction step.
- The fixed language applies equally to full-page navigation, HTMX fragments, and
  messages generated by Python, preventing mixed-language responses.
- External mail and user-entered case content remains faithful to its source language.
- A future multi-language effort must begin with a product decision and a representative
  catalog proof rather than adding ad-hoc translation keys to the current code.

## Evidence and review trigger

- [`base.html`](../../src/goldenage/web/templates/base.html) declares the fixed page
  language.
- [`app.py`](../../src/goldenage/web/app.py) contains the current English messages,
  shared HTMX/page context, and date-time formatters.
- [`config.py`](../../src/goldenage/config.py) defines the configurable local time zone
  and its `Europe/Berlin` default.
- [`tests/test_web_edges.py`](../../tests/test_web_edges.py) covers the current date-time
  conversion and formatting behavior.

Revisit this decision when product ownership identifies a supported non-English user
group, asks for a language choice, or requires locale-specific number/date formatting.
